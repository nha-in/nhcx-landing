# The CMS

Edit this site's words and its look in a browser, then publish. Python standard
library only: no install, no database, one process.

```sh
npm run cms                                   # http://127.0.0.1:8100
python3 cms/app.py --port 8100                # the same thing
NHCX_CMS_PASSWORD=… python3 cms/app.py --host 0.0.0.0
```

## What it edits

| Tab | File | What is in it |
| --- | --- | --- |
| Site content | `content/fallback.json` | Navigation, footer, the landing sections, the DevTools and apply pages |
| News | `content/news.json` | The news page's own copy, then its feed |
| Videos | `content/videos.json` | The videos page's own copy, then the library |
| Downloads | `content/download.json` | The groups and files the downloads page lists |
| Theme | `styles/globals.css` | The design tokens in `:root`: colours, corners, container width, fonts |

The content files have no schema and the editor does not impose one. It walks
whatever JSON it is given and draws a field per value: a short string gets an
input, a long one a text area, a number a number field, a list gets add, remove
and reorder. Add a field to a content file by hand and it appears here on the
next reload; nothing in the CMS needs to know about it.

Two files are deliberately **not** editable here. `content/adapter.json` is
generated by `npm run sync:adapter` from the nhcx-adapter GitHub release and any
edit would be overwritten on the next build. The documentation under
`public/docs/` is staged from the docs project by `npm run sync:docs`.

## Saving

Save writes the file. Publish runs `npm run build`, which regenerates `out/`,
and streams the log into the panel so a failure is visible rather than silent.

Four things stand between an edit and a broken site:

1. **A contract per file.** `news.json` must keep `page` and `items`,
   `download.json` its `groups`, and so on. A save that would drop one is
   refused with the reason, before anything is written.
2. **A backup.** The previous version is copied to `cms/backups/` first
   (the last 40 are kept), so any save can be undone by hand.
3. **An atomic write.** The new content goes to a temporary file in the same
   directory and is then renamed over the old one, so an interrupted save
   cannot leave a half-written file.
4. **A conflict check.** The editor sends back the modification time it loaded;
   if the file changed underneath it in the meantime the save is refused rather
   than silently overwriting whoever else was editing.

`Ctrl`/`Cmd`+`S` saves. Leaving a tab with unsaved changes asks first.

## Deployed at /cms

On the sandbox host it runs as a systemd service and nginx publishes it beside
the site, following the same pattern as the other apps here:

    ~/bin/cms                       the launcher: cd, read the env file, run
    /etc/systemd/system/cms.service  created by ~/bin/createService
    location /cms/                   in /etc/nginx/sites-enabled/default

    systemctl status cms · journalctl -u cms -f · systemctl restart cms

The process binds to `127.0.0.1:8100` only; nginx is what exposes it. Its
`proxy_pass` ends in a slash, so `/cms/` is stripped before the request reaches
the app, and `location = /cms` redirects to `/cms/` so the relative URLs in the
page resolve. Everything the UI asks for is addressed relative to wherever it
is mounted, so the same files work at `/` in development and `/cms/` here.

The password lives in `~/.config/nhcx-cms.env` (mode 600), which the launcher
sources. Change it there and `systemctl restart cms`.

## Access

With no `NHCX_CMS_PASSWORD` set, the server refuses to bind to anything but the
loopback address: an unauthenticated CMS should not be reachable from another
machine. Set a password to expose it, and put it behind TLS if that machine is
not on a trusted network. Sessions are cookies held in memory, so restarting the
server signs everyone out.
